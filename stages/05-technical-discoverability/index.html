GEO Lab #05: Technical Discoverability

What can a search-engine check actually tell me about whether people will discover my work through AI?

Author: Helen Bird · First published: 2026-11-06 · Updated: 2026-11-06

Technical learning record, not an AI-answer experiment. The observations below were collected on November 4–6, 2026. No new ChatGPT or Grok recommendations were measured. This page publishes reviewed aggregates; private raw engine/account evidence is excluded.

What I learned

  • A successful query can still leave indexing unknown. One Bing batch returned successful results for all 70 URLs, yet the returned fields did not establish that any page was indexed.
  • Access, crawling, indexing and recommendation need separate evidence. Seventy successful requests using a declared OpenAI crawler user agent demonstrate simulated access, not a real OpenAI crawler visit.
  • Submission and processing are different outcomes. Google accepted the Sitemap submission; its later processing flag was still pending. Bing separately reported a successful imported feed.
  • Keep failures visible. A later joint run hit Bing throttling after 11 successful URL queries. The failed request and 58 skipped positions remain in the history; they were not converted into indexing results.

These are time-bounded observations, not a controlled GEO intervention. The successful ten-second batch and later five-second batch differed in time as well as spacing. They cannot prove that one request interval caused the different outcomes.

Ask what each signal proves

  1. Configuration and access: canonical URLs, indexability directives, effective robots rules and HTTP access establish current technical conditions.
  2. Discovery and crawling: an engine-associated crawl timestamp or verified request log can show that a system encountered a page. A missing timestamp leaves that evidence unknown.
  3. Indexing: use the engine's explicit indexed-version verdict when available. Do not infer membership from a successful information query.
  4. AI retrieval and recommendation: test user questions separately, with repeat runs and original answers. Search-engine indexing alone does not supply this evidence.

The original GitHub Pages URL does not currently expose a confirmed owner-accessible per-request crawler log. Repository Traffic is not a substitute for a Pages access log. Real OAI-SearchBot access therefore remains UNKNOWN.

A small workflow I can keep using

  • Save a baseline before making changes. Keep manual observations and official API responses separate; do not backfill later results into an earlier date.
  • Reuse one canonical URL inventory. Record which routes belong in the Sitemap and which supplemental archives remain crawlable.
  • Keep engines separate. Save Google indexing, Bing information queries and OpenAI eligibility in their own snapshots.
  • Stop on throttling or access failures. Retain the first blocking response and every remaining unqueried URL as UNKNOWN with zero attempts.
  • Preserve history privately. Raw responses and account evidence stay outside the public Pages repository. Publish only reviewed summaries.
  • Notify only after evidence is durable. A completed, successful GitHub run and committed full snapshot precede the first complete-batch notification.

The recurring monitor is configured for Monday 10:17 Asia/Shanghai; GitHub may delay its start. Configuration and a manual workflow dispatch do not prove that the first scheduled occurrence has run. Ordinary Google indexing requests remain manual.

Bing returned ThrottleHost (official code 5) with HTTP 400. Treating only HTTP 429 as throttling would miss this case. The program now recognizes provider fault codes, stops the batch and records skipped positions. A successful earlier batch does not erase a later failure.

What I would reuse as an independent builder

  • Measure one layer at a time. Name the evidence you want before choosing an API or dashboard.
  • Use UNKNOWN as a real result. Missing or ambiguous fields should not become a negative indexing verdict.
  • Publish useful changes, then notify. A genuine report or corrected learning resource can create an eligible IndexNow change; a test edit, date-only change or repeated old URL does not establish a useful intervention.
  • Keep a change timeline. Technical fixes, Sitemap submission, manual indexing requests and later publication are separate events. Their effects cannot be pooled into one causal claim.

Still open in this snapshot: Google Sitemap processing, current Bing membership, real OpenAI crawler access, a real IndexNow receipt and a successful combined monitor run. New observations can close operational checks without proving recommendation lift.
